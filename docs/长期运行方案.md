# 长期运行方案（设计文档）

> 本方案仅作设计说明，描述每天运行并持续一年时的系统架构和运维策略。

## 1. 定时任务调度

### 方案: systemd timer + cron（Linux）或 Windows 任务计划程序

```
每天 02:00 执行采集（选择低峰时段）
每次执行: uv run python -m zhongshan_land_scraper.main --pages 10 --delay 2.0
```

**执行策略**:
- 首次全量采集（10页，约90条）
- 后续增量采集：利用断点续传机制，只采集新记录
- 每周一次全量刷新：强制 `--no-resume` 重新采集，发现已更新或新发布的记录
- 节假日自动跳过（配置节假日日历）

## 2. 增量采集设计

### 核心机制

1. **去重检查**: `ResumeManager` 维护 `seen_ids.json`，新记录以 `docId` 为唯一键
2. **发布时间过滤**: 列表 API 返回的记录按 `publishDate` 排序，仅处理比上次采集时间更新的记录
3. **状态更新检测**: 公告可能被修改或补充附件，每周全量刷新可捕获更新

### 增量流程

```
定时任务启动
  -> 加载 seen_ids.json
  -> 采集第1页列表
  -> 逐条检查 docId 是否已存在
     -> 已存在: 跳过
     -> 新记录: 采集详情 -> 保存 -> 标记成功
  -> 采集后续页（直到无新记录或到达最大页数）
  -> 生成输出文件
  -> 发送通知
```

## 3. 数据库存储设计

### SQLite 方案（轻量，无需服务器）

```sql
CREATE TABLE land_transactions (
    doc_id TEXT PRIMARY KEY,
    notice_id TEXT NOT NULL,
    notice_title TEXT,
    publish_date TEXT,
    project_code TEXT,
    project_owner TEXT,
    project_type_name TEXT,
    site_name TEXT,
    trading_process TEXT,
    transaction_date TEXT,
    winner TEXT,
    land_area TEXT,
    transaction_price TEXT,
    land_location TEXT,
    land_usage TEXT,
    transaction_agency TEXT,
    notice_nature TEXT,
    detail_url TEXT,
    html_path TEXT,
    txt_path TEXT,
    attachments TEXT,          -- JSON 数组
    field_sources TEXT,        -- JSON 对象
    verification_status TEXT,  -- 已核验 / 待核验
    missing_fields TEXT,       -- JSON 数组
    notes TEXT,
    captured_at TEXT,
    first_seen_at TEXT,        -- 首次采集时间
    last_updated_at TEXT,      -- 最后更新时间
    is_deleted INTEGER DEFAULT 0  -- 软删除标记
);

CREATE INDEX idx_publish_date ON land_transactions(publish_date);
CREATE INDEX idx_project_code ON land_transactions(project_code);
CREATE INDEX idx_capture_date ON land_transactions(captured_at);
```

### 数据库操作

- **插入**: 新记录时 INSERT
- **更新**: 发现记录变化时 UPDATE（`last_updated_at` 更新）
- **软删除**: 不再出现在列表中的记录标记 `is_deleted=1`
- **查询**: 支持按时间、区域、用途、价格区间筛选

## 4. 去重策略

### 当前实现

- 以 `docId`（`noticeId + tradingProcess`）为唯一键
- `seen_ids.json` 持久化到磁盘
- `--resume` 默认启用，自动跳过已采集项

### 一年期扩展

```python
# 数据库级别的去重
INSERT OR IGNORE INTO land_transactions (...) VALUES (...)

# 变更检测（每周全量刷新时）
UPDATE land_transactions SET
    last_updated_at = ?,
    verification_status = ?,
    notes = ?
WHERE doc_id = ? AND (
    notice_title != ? OR transaction_date != ? OR ...
)
```

## 6. 失败告警

### 告警触发条件

| 条件 | 阈值 | 告警方式 |
|------|------|----------|
| 采集失败率 > 10% | 单次运行 | 邮件/企业微信 |
| 连续 3 天无新记录 | 3天 | 邮件提醒 |
| 90004 错误超过 2 次 | 单次运行 | 立即告警 |
| 磁盘空间 < 1GB | 持续监控 | 告警 |
| 内存使用 > 80% | 持续监控 | 告警 |

## 7. 网站变化应对

### 监测机制

1. **结构变化检测**: 每次采集检查关键 DOM 选择器是否存在
2. **API 变化检测**: 检查响应 JSON 结构是否变化
3. **字段缺失率监控**: 如果待核验率突然上升，可能说明解析逻辑需要更新

### 应对策略

| 变化类型 | 检测方式 | 应对措施 |
|----------|----------|----------|
| DOM 选择器变化 | `locator.count() == 0` | 更新选择器，增加兼容性策略 |
| API 端点变化 | `expect_response` 超时 | 更新 URL 模式 |
| 反爬升级 | 90004 频繁出现 | 增加 delay，减少并发 |
| richtext 格式变化 | 字段提取率下降 | 更新解析逻辑 |
| 分页组件变化 | 下一页按钮找不到 | 更新分页策略 |

### 自动降级

```python
# 如果检测到结构变化，自动切换到保守模式
if field_extraction_rate < 0.5:
    log.error("site_structure_changed")
    send_alert("网站结构可能已变化", f"字段提取率: {field_extraction_rate}")
    # 停止自动采集，等待人工确认
    sys.exit(1)
```

## 8. 人工复核流程

### 待核验记录处理

1. **每日汇总**: 生成待核验记录清单
2. **人工检查**: 打开原始详情页 URL，手动核对缺失字段
3. **数据补录**: 在数据库中补充缺失字段，更新核验状态
4. **规则优化**: 如果某类缺失频繁出现，更新解析逻辑

### 复核工具

```bash
# 生成待核验清单
uv run python -c "
import json
with open('output/zhongshan_land_transactions.json') as f:
    records = json.load(f)
pending = [r for r in records if r['核验状态'] == '待核验']
for r in pending:
    print(f'{r[\"项目编号\"]}: {r[\"公告标题\"]}')
    print(f'  URL: {r[\"公告详情链接\"]}')
    print(f'  备注: {r[\"备注\"]}')
"
```

## 10. 成本控制

### 资源消耗估算（每日运行）

| 资源 | 单次消耗 | 月度估算 | 年度估算 |
|------|----------|----------|----------|
| CPU 时间 | ~15分钟 | ~7.5小时 | ~90小时 |
| 内存峰值 | ~500MB | - | - |
| 磁盘（原始数据） | ~100MB/天 | ~3GB | ~36GB |
| 网络流量 | ~50MB/天 | ~1.5GB | ~18GB |
| 云存储（备份） | - | ~$5 | ~$60 |

### 优化措施

1. **原始数据清理**: 30天后自动删除原始 HTML/截图，只保留结构化数据
2. **数据库压缩**: 定期 VACUUM 数据库
3. **增量采集**: 只采集新记录，减少不必要的详情页访问
4. **共享浏览器**: 单次运行中复用浏览器上下文，减少启动开销
5. **无头模式**: 生产环境使用 `--headless` 减少资源消耗

## 12. 监控仪表盘

### 关键指标

| 指标 | 目标值 | 告警阈值 |
|------|--------|----------|
| 每日新增记录数 | >= 1 | 连续3天=0 |
| 字段提取完整率 | >= 95% | < 90% |
| 采集成功率 | >= 98% | < 90% |
| 平均采集时间 | <= 20分钟 | > 30分钟 |
| 待核验记录占比 | <= 5% | > 10% |

### Grafana 仪表盘

```sql
-- 每日新增记录趋势
SELECT DATE(captured_at) as date, COUNT(*) as count
FROM land_transactions
GROUP BY DATE(captured_at)
ORDER BY date;

-- 字段完整率
SELECT 
    SUM(CASE WHEN verification_status='已核验' THEN 1 ELSE 0 END) * 100.0 / COUNT(*) as rate
FROM land_transactions;
```
