# 任务四：技术说明

## 一、任务理解

### 目标

从中山市公共资源交易平台 (`ygp.gdzwfw.gov.cn`) 采集土地使用权交易结果公告，提取以下核心字段：
- 成交时间、竞得人、用地面积、成交总价
- 宗地位置、土地用途、项目名称、项目编号
- 公告标题、发布时间、详情链接

### 数据用途

土地交易数据是区域经济分析、房地产市场研究、投资决策支持的重要基础数据。本采集工具将非结构化的网页公告转化为结构化的 Excel/JSON/CSV 数据，便于后续分析和使用。

### 约束条件

- 使用真实 Chrome 浏览器（非无头模式优先）
- 操作间隔 >= 1.2 秒
- 禁止并发访问
- 不逆向签名算法
- 禁止硬编码 Cookie/Token

## 二、网站和数据来源分析

### 网站架构

- **前端**: Vue.js SPA，hash 路由 (`/#/442000/jygg`)
- **后端**: RESTful API，动态签名验证
- **数据流**: 前端点击 -> 触发 API -> Vue 渲染列表/详情

### 关键发现

1. **列表数据**: 通过 `POST /search/v2/items` 获取，含分页信息
2. **详情数据**: 通过 `GET /trading-notice/new/detail` 获取，含 `tradingNoticeColumnModelList`
3. **DOM 与 API 差异**: "公告内容"栏目不渲染到 DOM，必须从 API 响应的 `richtext` 字段读取

### 筛选条件

- siteCode=442000（中山市）
- noticeSecondType=B（土地矿业）
- tradingProcess=3742（土地使用权交易结果公告）

## 三、动态签名及 90004 问题

### 签名机制

网站使用动态签名验证：
- 每次 API 请求携带 `Cookie` + `Nonce` + `Signature` + `Timestamp`
- 签名算法未知，无法逆向构造有效请求
- 旧签名在会话过期后返回 90004 "登录凭证失效"

### 应对策略

**不逆向签名，使用浏览器自动化**:

1. Playwright 启动真实 Chrome 浏览器
2. 网站自行建立匿名会话（自动设置 Cookie）
3. 用户正常点击筛选条件，触发 Vue 发起 API 请求
4. 浏览器自动附加有效签名，API 正常响应
5. 使用 `expect_response` / `requestfinished` 监听响应，获取 JSON 数据

### 90004 错误处理

```python
def _is_api_error_90004(data: dict) -> bool:
    code = data.get("code") or data.get("errcode")
    msg = str(data.get("msg", "")) + str(data.get("errmsg", ""))
    return code == 90004 or "登录凭证失效" in msg
```

出现 90004 时：
- 关闭当前浏览器
- 重新启动浏览器建立新会话（最多重试 1 次）
- 不无限重试，避免触发更严格的反爬

## 四、为什么使用 Playwright 监听响应

### 尝试过的方法

| 方法 | 结果 | 原因 |
|------|------|------|
| `page.route` + `route.fetch()` | 失败 | "Request context disposed" |
| `page.on("response")` + async handler | 不稳定 | 异步 handler 中无法可靠 await response.json() |
| `page.on("requestfinished")` | 可用但复杂 | 需要手动关联 request/response |
| `page.expect_response()` | **成功** | 支持 async context manager，响应对象稳定可用 |

### 最终方案

**列表页**: 使用 `page.on("response")` 监听器收集所有响应，取最后一个作为正确筛选结果。Vue 点击筛选条件时可能触发多次 API 请求（中间响应包含未完全筛选的数据），取最后一个可确保获得正确结果。

```python
async def _capture_list_api_with_listener(page, delay):
    responses = []
    def on_response(response):
        if LIST_API_URL in response.url and response.request.method == "POST":
            responses.append(response)
    page.on("response", on_response)
    # 点击筛选条件，等待所有响应完成
    await _apply_first_filter(page, delay)
    await _apply_second_filter(page, delay)
    await asyncio.sleep(5)
    # 取最后一个响应
    return await responses[-1].json()
```

**详情页**: `expect_response` 捕获 `GET /trading-notice/new/detail`

```python
async with detail_page.expect_response(
    lambda r: DETAIL_API_PATTERN in r.url,
    timeout=15_000,
) as response_info:
    await detail_page.goto(detail_url, wait_until="domcontentloaded")
response = await response_info.value
detail_api_data = await response.json()
```

**优势**:
- 不修改网站请求（不拦截、不篡改）
- 响应对象是标准 Playwright Response，可直接调用 `.json()`
- 超时控制明确，不会无限等待
- 代码简洁，易于维护

## 五、详情字段处理方法

### 字段来源优先级

1. **API richtext**（最高优先级）: 从 `tradingNoticeColumnModelList[1].richtext` 解析 HTML 表格
2. **DOM 表格**（补充）: 从页面渲染的"公告信息"表格提取
3. **公告标题**（兜底）: 从 `noticeTitle` 提取项目编号和土地用途

### 解析 HTML 表格

```python
def _parse_richtext_html(richtext_html: str) -> dict[str, str]:
    soup = BeautifulSoup(richtext_html, "html.parser")
    result = {}
    for table in soup.find_all("table"):
        for row in table.find_all("tr"):
            cells = row.find_all(["th", "td"])
            texts = [c.get_text(strip=True) for c in cells]
            # 模式1: 两列（标签 + 值）
            if len(texts) == 2:
                field = _match_field_name(texts[0])
                if field:
                    result[field] = texts[1]
            # 模式2: 四列（标签1 值1 标签2 值2）
            elif len(texts) == 4:
                for i in range(0, 4, 2):
                    field = _match_field_name(texts[i])
                    if field:
                        result[field] = texts[i + 1]
    return result
```

### 字段别名映射

支持多种标签写法：
- "竞得人" / "受让人" / "受让人名称" / "成交单位" / "竞买人" / "竞得单位"
- "用地面积" / "宗地面积" / "土地面积" / "出让面积" / "面积"
- "成交总价" / "成交价" / "成交金额" / "成交地价" / "总价"

### 字段冲突处理

当 API 和 DOM 对同一字段给出不同值时：
- API 字段优先（通常更准确）
- 记录 warning 日志，便于人工复核
- 典型场景："竞得人" 字段，API 和 DOM 值可能因括号内容不同而略有差异

## 六、去重和断点续传

### 去重机制

- **唯一键**: `docId = noticeId + "-" + tradingProcess`
- **检查时机**: 采集每条记录前
- **处理方式**: 已采集的记录直接跳过，不重复访问详情页

### 断点续传实现

```python
class ResumeManager:
    def __init__(self, output_dir: Path):
        self.seen_ids: set[str] = set()
        self.seen_ids_path = output_dir / "seen_ids.json"
        self._load()  # 启动时加载已有记录

    def is_seen(self, doc_id: str) -> bool:
        return doc_id in self.seen_ids

    def mark_success(self, doc_id: str) -> None:
        self.seen_ids.add(doc_id)
        self._save()  # 实时保存到磁盘
```

### 断点续传合并

`main.py` 中的 `_merge_with_existing` 函数在 resume 模式下加载已有的 `zhongshan_land_transactions.json`，与新记录合并（以 noticeId 为键，新记录优先），确保最终输出包含所有记录。

### 使用场景

1. **中断恢复**: 采集过程中断（网络问题/浏览器崩溃），重新运行自动跳过已采集项
2. **增量更新**: 定期运行，只采集新发布的公告
3. **手动重试**: 使用 `--no-resume` 强制从头开始

## 七、实际遇到的问题

### 1. 筛选条件触发多次 API 请求

**问题**: 点击"土地矿业"和"土地使用权交易结果公告"时，Vue 触发多次 `POST /search/v2/items` 请求：
- 第一次响应：只筛选了"土地矿业"，包含多种 tradingProcess（3C14、3C42 等工程建设公告）
- 第二次响应：加上了"土地使用权交易结果公告"筛选，但混入 1 条 3711 出让公告
- 第三次响应：最终正确结果，全部为 3742

**解决**: 使用 `page.on("response")` 监听器收集所有响应，取最后一个作为正确结果。同时添加 `_validate_list_items` 函数，每页数据写入前校验所有记录的 tradingProcess==3742 且标题包含"结果公告"。

### 2. 分页组件识别

**问题**: 分页使用自定义组件 `gd-pagination`，不是 Element UI 标准分页，传统选择器无法定位。

**解决**: 通过 HTML 结构分析发现：
- 左箭头按钮（icon-left）— 上一页
- 输入框（type=number）— 当前页码
- `/ N` — 总页数
- "跳转"按钮
- 右箭头按钮（icon-right）— 下一页

实现双重策略：优先点击右箭头，如被隐藏则通过输入框+跳转按钮翻页。

### 3. 详情页打开方式

**问题**: 最初通过点击列表项打开详情页，但点击后新页面打开时机不确定，API 监听器注册困难。

**解决**: 改为直接导航到详情页 URL（从列表项数据构造），在 expect_response 中注册监听器后再执行 goto，响应捕获更可靠。

### 4. richtext 中的 HTML 表格解析

**问题**: richtext 中的表格不是标准 HTML，可能包含 `colspan` / `rowspan`，简单的 `find_all("td")` 可能错位。

**解决**: 实现两种模式：
- 模式1: 一行两列（th + td 或 td + td）
- 模式2: 一行四列（标签1 值1 标签2 值2）

并增加字段别名匹配，提高容错性。

### 5. Windows 终端中文显示乱码

**问题**: PowerShell / Git Bash 中中文输出显示为乱码。

**解决**: 这不是数据问题，是终端编码问题。实际数据文件（JSON/CSV/Excel）编码正确。使用 `chcp 65001` 可修复终端显示。

## 十、方案不足和改进

### 当前不足

1. **单进程串行**: 每条记录详情页依次访问，100条记录耗时约15-20分钟
2. **浏览器重启开销**: 每次运行启动新浏览器，每次约3-5秒
3. **richtext 解析脆弱**: 依赖 HTML 表格结构，网站改版可能破坏解析
4. **无可视化监控**: 采集进度只能通过日志观察
5. **缺失字段处理简单**: 仅标记"待核验"，未自动尝试补充

### 改进方向

1. **并发优化**: 在反爬允许范围内，使用 2-3 个浏览器上下文并行采集详情页
2. **浏览器复用**: 增量采集时复用上次的浏览器上下文
3. **结构化解析**: 使用 LLM 或更鲁棒的 HTML 解析策略（如基于视觉布局的解析）
4. **Web 仪表盘**: 提供实时采集进度、字段提取率、错误率的可视化
5. **智能补全**: 对缺失字段尝试从附件 PDF 或关联公告中补充
6. **数据库存储**: 使用 SQLite/PostgreSQL 替代 JSON 文件，支持查询和更新
